# H. 交接檔案 SOP

> 觸發詞：老闆說「**準備交接檔案**」或「**開始新對話**」時，主動完成本檔全部步驟，不用老闆逐項交代。
> 本檔可被模型依 F 協議 §1「按 CLAUDE.md 規則更新」的精神小幅修正（例：驗證指令隨專案演進調整），
> 結構性變動（改觸發詞、改交接落點）仍需老闆同意。

## 適用專案：本專案是 Python/FastAPI（無 `package.json`），harness 放在 `docs/harness/`

**注意**：這份 SOP 對應的是「這個」專案的實際結構。若你在別的專案看過類似流程用了
`.claude/harness/00-INDEX.md`、`06-HANDOVER-LETTER.md`、`npm run build/lint` 等路徑或指令，
那是別的專案的規格，**在本專案一律不適用**——本專案唯一真實存在的交接載體是 `docs/PROGRESS.md`。

## 收到觸發詞時，依序做這 4 件事

### 1. 更新 `docs/PROGRESS.md`「最新狀態」區頂部條目

若本次 session 已經有頂部條目（多數情況會有，因為 CLAUDE.md 開發循環步驟 7 規定完成功能就要更新），
把它**擴充**成完整交接格式；若還沒有條目，新增一則。必須包含五項：

- **任務目標**：老闆這次要求做什麼
- **已完成到哪**：逐項列出，附涉及的檔案路徑與 commit hash
- **下一步是什麼**：具體待辦，分「已核准可做」和「待老闆決策」
- **涉及檔案路徑**：改過的檔案清單（相對路徑，可用 markdown link）
- **User 已核准 vs 尚未核准的事項**：明確切開，避免下個 session 誤把「討論過的想法」當「核准的任務」

### 2. 踩坑檢查（依 F 協議 §2）

本 session 有沒有「花 >2 輪嘗試才解決、且未來可能再犯」的坑？
- 有 → 依 F 協議 §2 的五欄格式追加進 `docs/harness/LESSONS.md`
- 沒有 → 略過，不用硬湊

**教訓內容的紅線**：不得寫成「遇到權限阻擋/安全機制就換方法繞過」這類指令。
本專案的 auto-mode 分類器會攔下這類條目（曾實際發生），因為在真金交易系統裡，
教未來模型「被擋就繞過去」是比原始踩坑本身更危險的模式。若真的遇到工具被擋，
教訓要寫「為什麼會被擋、下次怎麼避免觸發擋下」，不要寫「被擋了就換工具硬過」。

### 3. 跑驗證，結果記入 PROGRESS.md 條目

```
python -m py_compile <本次改過的每一個 .py 檔>
python -m pytest tests/unit -x -q
git status --short
```

**本專案沒有 `npm run build` / `npm run lint`**（無 Node 專案結構）。上面三行才是這裡的驗證指令。
把 pytest 通過筆數與 git status 是否乾淨寫進 PROGRESS.md 條目尾端。

### 4. Commit + push

跟 CLAUDE.md 開發循環步驟 5 一樣：`git add <明確檔名>`（禁止 `-A`/`.`）→ commit → push。
交接文件本身的改動用 `docs:` commit 前綴。

## 新對話開場白（老闆可以直接複製貼上，或說更短的話讓模型自己套用）

> 開工前先讀 `docs/PROGRESS.md` 前 40 行 + `git status`，接續處理〈某某項目〉。

這其實就是 CLAUDE.md「Session 啟動」四步驟本來就會做的事——新對話不需要記住任何特殊路徑，
只要正常啟動就會自動讀到上一個 session 留的交接內容。老闆想額外強調重點時才需要加這句話。
