# F. 知識迭代與反思協議

> 回答一個問題：後續模型怎麼安全地更新這套 harness，而不把它改爛。
> 原則：**經驗可以自由累積，規則本體動之前要有人類點頭。**

---

## §1. 權限分級表（想改任何 harness 檔案前先查這裡）

| 檔案 | 模型可自行修改？ | 說明 |
|------|------------------|------|
| `LESSONS.md` | ✅ 自由**追加**（不可刪改既有列）| 踩坑就寫，格式見 §2 |
| `IMPL-MAP.md` | ✅ 僅限行號校準與新增章節列 | 規格書變動後跑 grep 重算 |
| `docs/PROGRESS.md` | ✅ 按 CLAUDE.md 規則更新 | 日常工作的一部分 |
| `README.md`（harness 索引）| ⚠️ 僅限修正失效路徑 | 結構變動需老闆同意 |
| `CLAUDE.md` | ❌ 需老闆明示同意 | 路由中心，改壞全員迷路 |
| `C / D / E` 規則本體 | ❌ 需老闆明示同意 | 可先把修改提案寫進 LESSONS.md 備註欄暫存 |
| `A-diagnosis.md` / `G-handover.md` | ❌ 凍結（歷史文件）| 永不修改 |
| `.claude/settings.json` | ❌ 需老闆明示同意 | 權限防線，模型不得自行放寬（收緊也要報備）|
| `.gitignore` / CI workflows | ❌ 需老闆明示同意 | 破壞性變更 |

「老闆明示同意」= 對話中老闆針對**這一次具體修改**說了同意。上週同意過別的改動不算。

## §2. 踩坑紀錄的寫入標準（LESSONS.md）

**什麼算「坑」值得寫**：花了 > 2 輪嘗試才解決、且未來可能再犯的問題。
**什麼不算**：一次就修好的普通 bug、純粹自己手滑的 typo。

格式（表格一列五欄）：
`| 日期 | 症狀 | 根因 | 教訓（一句話，可執行）| 相關 commit |`

教訓欄的判準：**必須是一條未來可以直接執行的指令或檢查**，不是感想。
- ✅ 正例：「所有外部 IO 必包 asyncio.wait_for，timeout 後 pool.shutdown(wait=False)」
- ❌ 反例：「以後要更小心處理併發問題」（不可執行，禁止寫入）

## §3. 修改規則本體的流程（需同意類）

1. 把提案寫成一句話 + 動機，放進當次回覆問老闆：
   「提議修改 D 檔 §2：新增判準『XXX』，因為（引用 LESSONS 哪一條）」
2. 老闆同意 → 修改前先備份（Bash 工具：`cp <檔> <檔>.bak`）→ 修改 → 在檔案頂部 `>` 引言區加一行變更紀錄（日期 + 一句話）
3. 老闆沒同意或沒回應 → 提案寫進 LESSONS.md 的教訓欄尾端加註「【規則提案，待審】」，不動規則檔

## §4. 精簡與抽象化觸發器（防止經驗堆成垃圾山）

| 觸發條件 | 動作 |
|----------|------|
| `LESSONS.md` 超過 **150 行** | 觸發精簡：把同類坑合併為一條通則（例：三條 NaN 坑 → 一條「yfinance 數值必過 isnan」），合併後的通則若夠普遍，提案升格進 D 檔（走 §3 流程）|
| `PROGRESS.md` 超過 **250 行** | 「最新狀態」區只留最近 5 個 session，其餘壓縮成單行摘要移到檔尾歷史區 |
| 精簡本身 | 精簡 = 修改既有內容，**不在 §1「自由追加」的授權範圍內** → 精簡前先問老闆，且先備份（Bash 工具：`cp LESSONS.md LESSONS.md.bak`；PowerShell：`Copy-Item`），並在回覆中報告刪了什麼 |

## §5. 每次 session 收尾的反思三問（寫進最後一則回覆，30 秒完成）

1. 這次有沒有踩新坑？→ 有就寫 LESSONS.md
2. 有沒有哪條 harness 規則實際上妨礙了工作？→ 寫規則提案（§3）
3. PROGRESS.md 更新了嗎？→ 沒更新不准結束
