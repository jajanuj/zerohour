# G. 給未來 Session 的交接信

> 執筆：Fable 5，2026-07-04。這是我在本環境的唯一一次 session。
> 本檔凍結不修改。讀者：接手大任務前的任何模型，以及半年後想知道「當初為什麼這樣設計」的老闆。

## 一、三件老闆沒問、但我認為最關鍵的事

### 1. 最大的風險不是代碼寫壞，是「自信地動了不該動的東西」

這個系統的 bug 分兩種：網頁壞掉（可逆，老闆截圖罵一下就修）和
**交易邏輯錯誤（不可逆，賠真錢）**。歷史上所有事故都是第一種，所以模型會產生
「出錯也還好」的錯覺——直到有一天改壞 `position_sizer` 的公式而測試恰好沒覆蓋到。
這就是紅線表把 `src/risk/`、`src/signals/` 單獨列出的原因。另外一個現在就存在的洞：
**API 完全沒有認證**，任何知道網址的人都能 POST `/api/v1/tasks/generate_signal` 觸發下單流程、
燒 Gemini 配額。X-API-Key 大約 30 分鐘工作量，建議老闆盡快排上（PROGRESS 下一步候選 #1）。

### 2. 這個環境有兩道看不見的資源天花板，碰到就是詭異故障

- **記憶體 256MB（web 進程）**：不會報「記憶體不足」，只會突然 502。任何「加個並發」「加個套件」
  「載入個 DataFrame」都在消耗它。判準：ThreadPoolExecutor 全域總並發 ≤ 6；新依賴一律先問老闆。
- **Gemini 免費額度 RPD 20（每天 20 次請求）**：排程任務平日吃 5–6 次、週日 10 次。
  任何「加個 AI 分析」的功能都可能讓**既有排程任務靜默失敗**（配額耗盡不會有明顯報錯）。
  改 AI 相關功能前先算：平日餘額只有 ~14 次。

### 3. 老闆的驗收方式是「在生產環境截圖」——所以你要比他先看到問題

觀察本專案歷史：老闆用真實網站測試，發現問題後貼截圖回來。這意味著每一個沒自測的 bug
都會變成一次生產事故 + 一輪來回溝通。倒推出的行為準則：**改前端必先自己跑
`python -m pytest tests/e2e -x -q` 或 Playwright 截圖看過**；改後端必先 curl 過。
「老闆發現 bug」在這套 harness 裡定義為驗收流程失敗，不是正常迭代。

## 三、本 session 未完成事項（接手者請向老闆確認後處理）

1. **deploy.yml 測試閘門**：patch 全文在 `A-diagnosis.md` 痛點三。老闆說「同意 CI patch」即可套用。
2. **權限 allow 清單**：我想加 `git status/diff/log`、`py_compile`、`pytest tests/unit` 免確認，
   被 auto-mode 分類器擋下（模型不可自行擴權——合理）。老闆可自行加進 `.claude/settings.json`
   的 `"allow"` 陣列，或跑 `/fewer-permission-prompts`。
3. **`.env.tmp` 檔案本體還在磁碟上**：我已讓 gitignore 擋住它，但檔案含活密鑰，
   建議老闆親手確認內容已合併進正式管道後刪除（模型被 deny 讀取它，這是故意的）。
4. **API 認證（X-API-Key）**：未實作，優先級最高的下一個功能。

## 四、給接手模型的最後一句話

這套 harness 的每一條規則都對應一次真實付過的學費（A 診斷書和 LESSONS 有帳）。
你會在某個時刻覺得某條規則「在這個情況下顯然可以跳過」——那個時刻，就是規則在保護你的時刻。
照 F §3 提案修改它，但不要繞過它。
